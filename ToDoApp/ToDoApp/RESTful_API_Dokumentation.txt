RESTful API Dokumentation - ToDo App
====================================

Projekt: ToDo App
Backend: CodeIgniter 4 / PHP
Frontend: Vue 3 / Vite
Datenbank: MySQL
API-Basis-URL lokal: http://127.0.0.1:8080/api
Frontend lokal: http://127.0.0.1:5173


1. Projektübersicht
-------------------

Die ToDo App besteht aus einem Backend und einem Frontend. Das Backend stellt
eine RESTful API für TODO-Aufgaben und TODO-Kategorien bereit. Das Frontend
verwendet diese API, um Kategorien und Aufgaben anzuzeigen, zu erstellen, zu
bearbeiten und zu löschen.

Die API arbeitet vollständig mit JSON. Eingabedaten werden als JSON im Request
Body gesendet. Antworten werden ebenfalls als gültige JSON-Daten zurückgegeben.
Fehler werden mit sinnvollen Fehlermeldungen und passenden HTTP-Statuscodes
beantwortet.

Zusätzlich sind API Keys, JWT-Authentifizierung für geschützte Bereiche,
Pagination, Sortierung, Filterung und Logging umgesetzt.


2. Projektstruktur
------------------

Wichtige Projektbereiche:

- backend/
  Enthält die CodeIgniter-Backend-Applikation.

- backend/app/Config/Routes.php
  Definiert alle API-Routen.

- backend/app/Controllers/Api/CategoriesController.php
  Enthält die API-Logik für Kategorien.

- backend/app/Controllers/Api/TodosController.php
  Enthält die API-Logik für TODO-Aufgaben.

- backend/app/Controllers/Api/AuthController.php
  Erstellt JWT Tokens nach erfolgreichem Login.

- backend/app/Controllers/Api/ProtectedController.php
  Beispiel für einen geschützten API-Bereich mit JWT.

- backend/app/Config/Api.php
  Enthält die API Keys und JWT-Konfiguration.

- backend/app/Filters/ApiKeyFilter.php
  Prüft den API Key.

- backend/app/Filters/JwtAuthFilter.php
  Prüft den JWT Bearer Token.

- backend/app/Filters/ApiLogFilter.php
  Loggt API-Anfragen.

- backend/app/Database/Migrations/
  Enthält die Datenbank-Migrationen für Kategorien, TODOs, Kontakte und Logs.

- frontend/
  Enthält die Vue-Frontend-Applikation.

- frontend/src/App.vue
  Hauptansicht der ToDo App. Ruft die RESTful API auf.

-----------------------------------

4. Authentifizierung mit API Key
--------------------------------

Alle RESTful API-Endpunkte sind durch einen API Key geschützt. Ohne gültigen API
Key wird die Anfrage mit HTTP 401 abgelehnt.

Der API Key kann auf zwei Arten gesendet werden:

Variante 1: HTTP Header

X-API-Key: dev-frontend-key-2026

Variante 2: URL-Parameter

?key=dev-frontend-key-2026

Aktuell konfigurierte API Keys:

- dev-frontend-key-2026
  Benutzerkennung für Logs: frontend-dev

- dev-admin-key-2026
  Benutzerkennung für Logs: admin-dev

Beispiel ohne gültigen API Key:

GET /api/todos

Antwort:

HTTP Status: 401 Unauthorized

{
  "message": "Ungueltiger oder fehlender API Key.",
  "errors": {
    "key": "Senden Sie einen gueltigen API Key per X-API-Key Header oder ?key= URL-Parameter."
  }
}


5. JWT-Authentifizierung für geschützte Bereiche
------------------------------------------------

Zusätzlich zum API Key gibt es einen geschützten Bereich, der nur mit einem
gültigen JSON Web Token erreichbar ist.

Login-Endpunkt:

POST /api/auth/login

Benötigte Header:

Content-Type: application/json
X-API-Key: dev-frontend-key-2026

Request Body:

{
  "username": "admin",
  "password": "Admin123!"
}

Erfolgreiche Antwort:

HTTP Status: 200 OK

{
  "message": "Login erfolgreich.",
  "token_type": "Bearer",
  "expires_in": 3600,
  "access_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..."
}

Der erhaltene Token wird anschließend im Authorization Header gesendet:

Authorization: Bearer <access_token>

Geschützter Endpunkt:

GET /api/protected

Benötigte Header:

X-API-Key: dev-frontend-key-2026
Authorization: Bearer <access_token>

Erfolgreiche Antwort:

HTTP Status: 200 OK

{
  "message": "Geschuetzter Bereich erreichbar.",
  "data": {
    "user": "admin",
    "name": "API Admin"
  }
}

Antwort ohne JWT:

HTTP Status: 401 Unauthorized

{
  "message": "JWT fehlt im Authorization Header.",
  "errors": {
    "authorization": "JWT fehlt im Authorization Header."
  }
}


6. Allgemeine API-Regeln
------------------------

Datenformat:

- Requests mit Daten verwenden JSON.
- Antworten werden immer als JSON zurückgegeben.
- Der Header Content-Type sollte application/json sein.

Validierung:

- IDs in der URL müssen positive Zahlen sein.
- Pflichtfelder werden geprüft.
- Ungültige JSON-Daten werden abgelehnt.
- Nicht vorhandene Datensätze werden mit HTTP 404 beantwortet.
- Ungültige Eingaben werden mit HTTP 400 oder 422 beantwortet.
- Fachliche Konflikte werden mit HTTP 409 beantwortet.

Pagination:

GET-Endpunkte unterstützen:

- limit
  Anzahl Datensätze pro Seite. Erlaubt: 1 bis 100.

- page
  Aktuelle Seite. Muss mindestens 1 sein.

Beispiel:

GET /api/todos?limit=50&page=1

Sortierung:

GET-Endpunkte unterstützen:

- order_by
  Feld, nach dem sortiert wird.

- direction
  Sortierrichtung. Erlaubt: asc oder desc.

Beispiel:

GET /api/todos?order_by=date&direction=asc

Filterung:

TODOs können nach Kategorie gefiltert werden:

GET /api/todos?category_id=123


7. Datenmodell Kategorie
------------------------

Eine Kategorie wird im Frontend als Bereich angezeigt.

Felder in API-Antworten:

- id
  Eindeutige ID der Kategorie.

- name
  Name der Kategorie.

- description
  Beschreibung der Kategorie.

- isProtected
  Gibt an, ob die Kategorie geschützt ist.

- isUnlocked
  Gibt an, ob die Kategorie im Frontend entsperrt ist.

- createdAt
  Erstellungsdatum.

- updatedAt
  Änderungsdatum.

Beispiel:

{
  "id": 1,
  "name": "Schule",
  "description": "Aufgaben fuer Unterricht und Projektarbeit.",
  "isProtected": false,
  "isUnlocked": true,
  "createdAt": "2026-06-03 12:00:00",
  "updatedAt": "2026-06-03 12:00:00"
}

8.5 Kategorie löschen

Art der Anfrage:

DELETE /api/categories/{id}

Fachliche Regel:

Eine Kategorie darf nur gelöscht werden, wenn sich keine TODO-Aufgaben mehr in
dieser Kategorie befinden. Sind noch TODOs vorhanden, wird die Anfrage mit HTTP
409 abgelehnt.

Erfolgreiche Antwort:

HTTP Status: 200 OK

{
  "message": "Kategorie wurde geloescht."
}

Fehler, wenn noch TODOs vorhanden sind:

HTTP Status: 409 Conflict

{
  "message": "Kategorie kann nicht geloescht werden, solange TODO-Aufgaben darin vorhanden sind.",
  "errors": {
    "category_id": "Verschieben oder loeschen Sie zuerst alle TODO-Aufgaben dieser Kategorie."
  }
}

11. Fehlerantworten und HTTP-Statuscodes
----------------------------------------

Die API verwendet sinnvolle HTTP-Statuscodes:

- 200 OK
  Anfrage erfolgreich.

- 201 Created
  Neuer Datensatz wurde erstellt.

- 400 Bad Request
  Ungültige URL-Parameter oder ungültige Anfrage.

- 401 Unauthorized
  API Key fehlt, API Key ist ungültig oder JWT fehlt.

- 403 Forbidden
  Zugriff verweigert, zum Beispiel falsches Passwort.

- 404 Not Found
  Datensatz existiert nicht.

- 409 Conflict
  Fachlicher Konflikt, zum Beispiel Kategorie enthält noch TODOs.

- 422 Unprocessable Entity
  JSON-Daten wurden verstanden, sind aber inhaltlich ungültig.

- 503 Service Unavailable
  Datenbank ist nicht erreichbar.

Standardformat für Fehler:

{
  "message": "Beschreibung des Fehlers.",
  "errors": {
    "feldname": "Genaue Fehlermeldung."
  }
}


12. Logging
-----------

Jede API-Anfrage wird geloggt. Dadurch ist nachvollziehbar, welcher API-Benutzer
welche Anfrage ausgeführt hat.

Geloggte Informationen:

- API-Benutzer aus dem API Key
- HTTP-Methode
- Pfad
- Query String
- HTTP-Statuscode
- IP-Adresse
- Zeitpunkt der Anfrage

Die Logs werden über den CodeIgniter Logger geschrieben. Zusätzlich können sie
in der Datenbanktabelle api_request_logs gespeichert werden, sobald die
entsprechende Migration ausgeführt wurde.

Beispiel für einen Log-Eintrag inhaltlich:

{
  "api_user": "frontend-dev",
  "method": "POST",
  "path": "/api/categories",
  "query_string": "",
  "status_code": 201,
  "ip_address": "127.0.0.1",
  "created_at": "2026-06-03 12:00:00"
}


13. CORS und Frontend-Anbindung
-------------------------------

Das Frontend läuft lokal auf:

http://127.0.0.1:5173

Das Backend läuft lokal auf:

http://127.0.0.1:8080

Da Frontend und Backend auf verschiedenen Ports laufen, wird CORS benötigt.
Die API erlaubt deshalb die nötigen Header:

- Content-Type
- Authorization
- X-Requested-With
- X-API-Key

Auch OPTIONS-Preflight-Anfragen werden beantwortet. Das ist wichtig, weil der
Browser vor POST, PUT, PATCH oder DELETE mit eigenen Headern zuerst eine
OPTIONS-Anfrage sendet.

Das Frontend sendet den API Key automatisch im Header:

X-API-Key: dev-frontend-key-2026

16. Persönliches Feedback der Projektarbeit
-------------------------------------------

Die Projektarbeit war anspruchsvoll, weil nicht nur einfache CRUD-Funktionen
umgesetzt werden mussten, sondern eine vollständige RESTful API mit
Authentifizierung, Validierung, Fehlerbehandlung, Datenbankanbindung und
Frontend-Integration.

Besonders wichtig war es, die API nicht nur funktional zu machen, sondern auch
stabil und nachvollziehbar. Dazu gehören klare HTTP-Statuscodes, verständliche
JSON-Fehlermeldungen und Logging für jede Anfrage. Dadurch kann man Fehler
schneller finden und später besser nachvollziehen, welcher API-Benutzer welche
Aktion ausgeführt hat.

Ein wichtiger Lernpunkt war die saubere Trennung zwischen Backend und Frontend.
Das Frontend soll nur die API verwenden und keine direkte Datenbanklogik kennen.
Das Backend übernimmt Validierung, Speicherung und Sicherheitsprüfungen. Dadurch
ist die Architektur übersichtlicher und besser wartbar.

Auch die CORS-Konfiguration war ein wichtiger Teil der Arbeit. Da Frontend und
Backend lokal auf verschiedenen Ports laufen, muss der Browser Preflight-
Anfragen korrekt beantwortet bekommen. Erst dadurch können POST-, PUT-, PATCH-
und DELETE-Anfragen mit API-Key-Header zuverlässig funktionieren.

Insgesamt zeigt das Projekt, wie eine moderne Webanwendung aufgebaut werden
kann: Ein Vue-Frontend kommuniziert über eine JSON-basierte RESTful API mit
einem CodeIgniter-Backend, das Daten validiert, speichert, schützt und
protokolliert. Die wichtigsten Anforderungen der Aufgabenstellung wurden damit
systematisch umgesetzt.
